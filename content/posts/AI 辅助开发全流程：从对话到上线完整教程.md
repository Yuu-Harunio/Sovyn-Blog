> 适合零基础读者，读完即可独立完成一个个人博客从规划到部署的全过程。

> **开篇摘要**：本教程基于一个真实案例整理——零框架、零数据库、零运行成本的个人静态博客（Obsidian 知识库直发布），全程在 AI 辅助下完成开发并部署到 Cloudflare。从需求对齐、样式审查、正式开发、部署上线到排错迭代，覆盖完整流程。你可以把这套方法套用到任何小型项目上。

## 一、核心心法：AI 是"资深工程师"，你是"产品经理"

与 AI 协作开发，最重要的不是技术，而是**角色分工**。你要做的不是写代码，而是做决策、提需求、审结果。

| 你负责                 | AI 负责                |
| :--------------------- | :--------------------- |
| 提需求、做决策、审样式 | 技术选型、写代码、排错 |
| 说清"我要什么"         | 决定"怎么实现"         |
| 验收每个阶段的成果     | 修复验收中发现的问题   |

一句话总结：**你不要写代码，但你要看懂结果、及时反馈。**

------

## 二、完整流程：六个阶段

### 阶段 1：需求对话（不动手，先对齐）

**关键操作：明确告诉 AI"先别写代码"。**

这是新手最容易跳过、也最致命的一步。直接让 AI"帮我做个博客"，它会立刻生成一堆你不想要的代码。正确的开场是：

text

```
先不要动手生成，先进行基本的对话模式。
我想创建一个 Cloudflare Worker 部署的静态个人博客……
你先整体规划，不要进行本地项目的开发。
```



然后在这个阶段把这些问题全部聊清楚：

- **参考物**：给 AI 一两个你喜欢的网站链接 + 它们的开源仓库（如果有）
- **明确边界**：不要什么（"不要登录功能"、"不要 R2，因为要绑卡"）
- **成本约束**：("总预算 0 元")
- **内容规模**：("不超过一百篇文章"、"从 Obsidian 知识库导入")

AI 会输出技术选型、页面清单、部署流程的完整规划。**不满意就继续对话修正，满意了再进入下一阶段。**

> 💡 本案例在这一阶段的产出：纯静态方案 + Cloudflare Workers Static Assets + GitHub Actions 自动部署，明确砍掉登录、评论、数据库。

------

### 阶段 2：样式审查（先看"毛坯房"，再搞"装修"）

**关键操作：让 AI 先做一个独立的示例页面（HTML 单文件），不实现任何真实功能。**

text

```
先单独做一个示例页面给我，不需要实现真正的各种功能，
只是方便让我审查前端网页的样式和布局，看我是否有遗漏什么功能。
```



为什么这一步价值巨大：

1. 示例页双击就能在浏览器打开，**零环境依赖**就能验收
2. 样式问题（颜色、间距、布局比例）在示例页上改，成本几乎为零；等正式代码写完再大改，等于返工两遍
3. 你会在这个阶段发现"我以为我想要、其实我不想要"的东西

**审查示例页的正确姿势——提具体反馈，而不是"再好看点"：**

- ❌ "样式有点丑" → AI 只能瞎猜
- ✅ "正文宽度不符合比例，大纲最多占屏宽四分之一到三分之一" → 精准修改
- ✅ "导航栏我只要首页、标签、文章总览三个" → 明确边界
- ✅ "双链样式丑，其实就是文末列个相关文章链接，可以简化成单向跳转" → 砍掉过度设计

一轮一轮改，每轮只改你反馈的点。**直到你说"可以了，开始开发"为止。**

> 💡 本案例在示例页阶段迭代了 3 轮：修导航栏 → 修正文宽度和大纲比例 → 定稿。总耗时几分钟，避免了正式开发后的整体返工。

------

### 阶段 3：正式开发（一次性交付 + 本地验收）

样式定稿后，直接放权：

text

```
可以进行开发了。
```



AI 会完成：项目结构搭建、构建脚本、全部页面、配置文件、CI/CD 工作流。你这时候要做的是**验收**：

1. 让 AI 启动本地预览（`wrangler dev`），你逐页点开看
2. 重点核对之前示例页确认过的样式是否都被正式实现
3. 有问题继续提，没问题进入部署

------

### 阶段 4：部署上线（跟着文档做"填空题"）

部署是 AI 帮不上手、必须你亲自操作的部分（涉及账号和密钥）。让 AI 输出一份**小白友好的部署文档**：

text

```
为我生成一份 markdown 文档，内容为纯小白怎么使用这个项目来进行部署。
```



好的部署文档应该具备：每个命令可直接复制粘贴、每个密钥写清"从哪个页面哪个按钮获取"、每步带验证方法。

> 💡 本案例的部署文档（GUIDE.md）包含：GitHub 建仓、Cloudflare API Token 创建、Secrets 配置、域名绑定、日常发文章流程、常见问题。

------

### 阶段 5：排错（贴日志，别贴截图描述）

**部署第一次跑通是小概率事件，报错是常态。** 排错的核心技巧只有一个：

**把完整的错误日志贴给 AI，而不是自己描述报错。**

text

```
❌ "部署失败了，好像是权限的问题"        ← AI 只能给你列五种可能
✅  把 Actions 日志里 Error 那段原文贴上  ← AI 直接告诉你改哪
```



> 💡 本案例真实踩坑记录，三次报错三次修复：

| 报错                     | 真实原因                         | 修复                             |
| :----------------------- | :------------------------------- | :------------------------------- |
| Node 20 弃用警告         | wrangler 3.x 太旧                | 升级到 wrangler 4                |
| `Missing entry-point`    | 旧版 wrangler 不支持纯静态部署   | 把 wrangler 4 写进依赖           |
| `Missing from lock file` | 改了 package.json 忘推 lock 文件 | 补推 + `npm ci` 改 `npm install` |
| 缺 API Token 环境变量    | Secrets 还没配                   | 按 AI 给的路径去 GitHub 配置     |

注意看：每次 AI 都是**根据具体报错文本**定位到唯一原因的。这证明贴日志 > 一切描述。

------

### 阶段 6：功能迭代（上线后持续小步演进）

网站上线不是终点。后续每次想加功能，重复一个小循环：

text

```
提需求（可行/不可行先让 AI 评估）
  → AI 改代码 + 本地验证 + 给你预览
  → 你确认效果
  → push 上线
```



> 💡 本案例上线后的第一轮迭代：Typora `.assets` 图片文件夹适配（真实用户习惯）、首页改"最新 3 篇 + 随机推荐一篇"、总览页改 4 列网格 + 站内搜索。其中"随机推荐"和"搜索"这种听起来要后端的功能，AI 用一个已有的 JSON 文件 + 几十行前端代码就实现了——**提需求时让 AI 先评估"好不好做"，它说好做你就放心提。**

## 三、进阶技巧：给项目建立"AI 记忆"

项目做完后，让 AI 再给你生成两份长期文档，下次继续开发（无论是不是同一个 AI）都能无缝衔接：

| 文档                     | 作用                                                         |
| :----------------------- | :----------------------------------------------------------- |
| **MAP.md（架构地图）**   | 给 AI 看：目录结构、核心函数职责、语法规则、排障路径、扩展指南。AI 拿到它就能"读懂"整个项目 |
| **GUIDE.md（使用手册）** | 给你自己看：怎么部署、怎么发文章、常见问题怎么查             |

提示词示例：

text

```
根据这个项目创建一个 MAP.md，给未来的 AI 维护者看。
不用动项目中已完成的文件，就新创建一个文件。
```



这样做的好处：一个月后你想加功能时，不用从头解释项目，直接让 AI 读 MAP.md。

## 五、完整复现：本项目的提示词全序列（优化版）

下面的提示词是从真实项目的原始对话中**提炼优化**后的版本：补全了原话中省略的意图、统一了结构（需求 → 约束 → 期望产出），比原话更通用、更不容易被 AI 误解。按顺序发送即可复刻同款博客；`[ ]` 内换成你的信息。

**本案例的真实输入参考（可直接使用）：**

- 参考网站（想要的表现效果）：`https://01mvp.com/`
- 参考开源项目：`https://github.com/01MVP/blog-starter`
- 参考个人博客：`https://blog.01mvp.com/`

### 第 1 步：整体规划（对齐需求，只要方案不要代码）

text

```
先不要动手写代码，我们先用对话把方案对齐。

我的情况：
- 已有一个托管在 Cloudflare 的域名（网站刚注册，暂无内容）
- 想用 Cloudflare Worker 部署一个静态个人博客
- 希望尽量利用 Cloudflare 的免费功能，总预算为 0

我期望的表现类似 [参考网站 URL]，功能上参考它，但不需要登录功能。

请先输出完整的项目规划：技术选型（前端/构建/托管/部署方式）、
页面清单、从开发到上线的全流程。先不要开始开发。
```



**这一步的关键设计**：

- 开头明确"先不要动手写代码"——AI 默认拿到需求就写码，必须先按住
- 把"预算 0""已有域名"这类背景一次性给全，避免选型时踩到付费方案
- 明确要的产出物是"规划文档"，而不是代码

### 第 2 步：收敛需求（划清"不要什么"）

text

```
继续对话梳理，先不开发。我要明确以下边界：

不要的：
- R2 存储等任何需要绑定付款方式的 Cloudflare 功能
- 评论、点赞等一切互动功能（纯内容分享定位）
- 账号登录、任何动态的增删改查

必须有的：
- 文章来源是我的 Obsidian 知识库，直接拷贝 markdown 进项目即可发布，
  因此必须兼容 Obsidian 原生语法（双向链接、可读性）
- 文章中的图片作为静态资源随项目一起上传
- 较为精美的前端样式
- 文章规模：不超过 100 篇

参照 [参考项目仓库 URL] 的思路，但不要照抄它的代码——
请独立开发一个精简版本，避免冗余代码拖慢响应速度。
```



**这一步的关键设计**：

- 用"不要的 / 必须有的"两栏式结构，边界零歧义
- "不要照抄、独立开发、避免冗余"单独强调——参考项目的完整度远超需求，不限制就会被带偏
- 说出真实理由（如"R2 要绑卡"），AI 才能给出正确的替代方案

### 第 3 步：补充功能细节 + 索要示例页

text

```
需求梳理最后补两点，然后进入样式审查环节：

1. 文章页需要有目录大纲（TOC）功能
2. markdown 代码块需要带一键复制按钮

在开始正式开发之前，请先单独做一个静态的示例页面（单个 HTML 文件），
包含首页和文章页的核心样式：导航栏、文章列表、正文排版、TOC、代码块、
双向链接等。不需要实现任何真实功能，数据写死即可，
目的是让我在浏览器里直接打开审查样式和布局，确认没有遗漏的功能。
```



**这一步的关键设计**：

- 明确示例页是"单个 HTML 文件、数据写死、无功能"——保证零环境依赖、双击就能看
- 列出你希望示例页包含的组件清单，AI 会照单做全，方便一次性审完

### 第 4 步：审查示例页（逐轮反馈模板）

text

```
先别进行项目开发，继续修改示例页。

问题反馈：
1. [组件] [具体问题 + 期望效果]
   例：导航栏改为三个功能：首页、标签、文章总览
   例：正文区域宽度不够，与侧栏比例失衡，请调整
   例：[组件] 样式不合适，其实我想要的效果是 [描述]

修改后让我再次审阅，样式确定之前不进入正式开发。
```



text

```
基本可以了，剩余调整：[最后一两条小问题，如宽度比例、某个交互]。
修改后我再确认一次。
```



text

```
样式没问题了，可以开始正式开发了。
```



**这一步的关键设计**：

- 每轮反馈开头重申"先别开发"，防止 AI 顺手把正式项目写了
- 反馈公式：**组件名 + 问题 + 期望效果**，拒绝形容词（"有点丑"→ 说清丑在哪、想要什么）
- 最后一轮只留小问题，收敛到"可以开发"的明确放行信号

### 第 5 步：验收正式开发

text

```
项目已完成本地构建，请启动本地预览，我来逐页验收。
（发现问题 → 继续按第 4 步的反馈模板提；没问题 → 进入部署）
```



### 第 6 步：索取部署文档 + 排错

text

```
不要动项目代码。请生成一份纯小白视角的部署教程（markdown 文档），包括：
- 从零把项目部署到 Cloudflare 的完整步骤（每个命令可直接复制）
- 之后如何把新的 markdown 文章添加到网站
- 涉及密钥/账号配置的地方，写清楚从哪个页面的哪个入口获取
```



部署报错时（把日志原文完整粘贴，不要自己转述）：

text

```
[粘贴 GitHub Actions / 部署日志的完整报错部分]
这是部署时的报错，帮我定位原因并给出修复方案。
```



**这一步的关键设计**：

- 部署文档先声明"不要动项目代码"——你只要文档，不是要它改东西
- 排错铁律：贴日志原文。转述会丢失关键信息（错误码、版本号、文件路径）

### 第 7 步：功能迭代（上线后，按需重复）

text

```
上线后发现几个问题 / 想加几个功能：

1. [问题现象 + 你的真实使用场景]
   例：图片不显示。我的知识库用 Typora + Obsidian 制作，
   图片放在与 md 同名的 .assets 文件夹里，请适配这种目录结构。
2. [功能需求 + 效果描述]
   例：首页"最新发布"只保留最新 3 篇，下面加一个随机推荐模块，
   每次刷新随机推荐一篇。
   如果这个功能不好实现或有隐患，可以直接放弃。
3. [功能需求 + 退出条件]
   例：总览页改成每行 4 篇的网格布局，并考虑加站内搜索。
   不好实现就放弃搜索功能。

请先评估可行性，再动手。
```



**这一步的关键设计**：

- 每条需求附带**退出条件**（"不好实现就放弃"）——给 AI 说"不"的权利，避免硬塞烂方案
- 描述问题时带上你的**真实使用习惯**（Typora 的 .assets 目录），AI 才能从根因上适配而不是打补丁

### 复现要点提醒

1. **顺序不能乱**：规划 → 示例页 → 反馈迭代 → 放行开发 → 部署 → 迭代
2. **每一步都先声明"不要动手"**，直到你明确放行——这是控制节奏的唯一开关
3. **反馈要具体**：宽度给比例、功能给清单、砍功能给理由
4. **报错贴原文**：描述报错得到猜测清单，贴日志得到唯一答案
5. **个性化信息**：参考网站、站点名、导航栏目、个人介绍、域名——都在 `[ ]` 处替换

------

## 六、避坑清单

1. **别跳过规划直接要代码**——返工成本是规划成本的十倍
2. **别用形容词提样式需求**——"好看一点"没有信息量，"宽度改成 X、颜色换成 Y"才有
3. **别只描述报错**——错误日志原文是 AI 排错的第一手证据
4. **别让 AI 自作主张 push/上线**——代码它可以写，发布永远你确认后手动做
5. **改了依赖文件记得一起提交**——package.json 和 package-lock.json 是一对，分开提交 CI 就挂
6. **功能宁少勿多**——"不好做就放弃"这句话帮你挡掉 80% 的过度设计

------

## 七、总结

整个流程回顾起来就是一条主线：

**对话对齐需求 → 示例页审样式 → 放权开发 → 文档引导部署 → 贴日志排错 → 小步迭代 → 沉淀项目记忆**

你全程没有写过一行代码，但每一步的关键决策都由你把控——这就是 AI 辅助开发的正确姿势。
